# 上线发布

用户是编程新手。需要用户登录或授权的步骤，把链接给用户并等待，不要替用户做决定。

## 流程

```
- [ ] 1. 发布前检查
- [ ] 2. 选发布方式
- [ ] 3. 版本号和更新日志
- [ ] 4. 发布
- [ ] 5. 上线后检查
- [ ] 6. 告诉用户怎么回滚
```

### 1. 发布前检查（任何一项不过就停下，告诉用户）

- `npm run build` 通过；有测试就跑测试。
- 上次 `/dev-test` 之后有没有没验收的改动；没测过就建议先跑 `/dev-test`。
- `git status` 干净，改动都已提交。
- 密钥检查：搜索代码里有没有 API Key、密码、token；确认 `.env` 写在 `.gitignore` 里。发现问题立刻停下。
- 数据提醒：数据在 localStorage 时，新地址里是空的。提醒用户先在旧地址"导出"备份，上线后再"导入"。项目还没有导出/导入功能，就建议先用 `/dev-feature` 做一个。

### 2. 选发布方式（问用户）

- **只在自己电脑上用**（推荐给个人工具）：在桌面做一个双击启动脚本（macOS 用 `.command` 文件：进入项目目录，执行 `npm run build`，再执行 `npx vite preview --port 4173 --strictPort --open`）。不需要部署，数据只在本机。
- **部署成网址**：默认用 Vercel，连接 GitHub 仓库，以后每次推送自动部署。需要用户在浏览器登录。提醒用户：公开网址任何人都能打开，不要放隐私数据；有隐私内容时，要么加访问密码，要么只在本机用。
- **桌面 App / 可安装网页（PWA）**：进阶方案，先确认用户是否真的需要。

### 3. 版本号和更新日志

- 版本号格式 `大.中.小`：修 bug 加小号（1.0.1），加功能加中号（1.1.0），大改版加大号（2.0.0）。同步修改 `package.json` 里的 `version`。
- 在 `CHANGELOG.md` 顶部追加：

```markdown
## 1.1.0 - YYYY-MM-DD
- 新增：…
- 修复：…
```

- 提交，并打标签 `git tag v1.1.0`。推送前先征得用户同意。

### 4. 发布

按用户选的方式执行。

### 5. 上线后检查

打开线上地址（或双击启动脚本），把验收清单的核心项走一遍，确认 Console 没有红字、数据已导入。

### 6. 回滚

告诉用户出问题时怎么退回：

- Vercel：在项目后台的部署列表里，把上一个正常的版本重新设为正式版本。
- 代码：回到上一个版本标签（比如 `v1.0.0`）重新发布。
- 数据：用发布前导出的备份文件重新导入。
