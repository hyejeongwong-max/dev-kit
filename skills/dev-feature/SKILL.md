# 迭代新功能

用户是编程新手，全程中文、少术语。一次只做一个功能。

## 流程

```
- [ ] 1. 读现状
- [ ] 2. 澄清需求
- [ ] 3. 定方案
- [ ] 4. 实现
- [ ] 5. 自检
- [ ] 6. 用户验收
- [ ] 7. 收尾存档
```

### 1. 读现状

先读 `AGENTS.md`、`docs/进度.md`、`docs/验收清单.md`（有的话）。运行 `git status`：有未提交的改动时先告诉用户，问是先提交还是先放弃，不要和这次改动混在一起。

### 2. 澄清需求

按模板补齐，缺什么就问，补齐后复述给用户确认：

```text
【要做什么】
【怎么用】（用户怎么操作，会看到什么）
【不要动】
【怎么算做完】（能亲手验证的标准；涉及数据时，至少一条是"刷新后还在"）
```

用户一次提了多个功能时，列出来让用户选先做哪个，其余写进 `docs/进度.md` 的"下一步打算"。

### 3. 定方案

用大白话说明：要改或新增哪些文件，数据存在哪（localStorage key），会不会影响已有数据和其他页面。

- 改动涉及 3 个以上文件、要新增依赖、或要改数据结构时，先等用户确认再动手（可以建议用户切到 Plan 模式）。
- 改数据结构：必须兼容旧数据（缺的字段给默认值），并提醒用户先导出备份。
- 新增依赖：说明用途和不装的替代办法，用户同意后再装。

### 4. 实现

只改需求范围内的代码，不顺手重构。沿用已有组件和 AGENTS.md 里的设计规范。单个文件超过 300 行时，提醒用户要不要拆分。

### 5. 自检

- `npm run build` 必须通过；`package.json` 里有 `test` 命令就也跑一遍。
- 能用浏览器工具时，亲自打开页面把主路径走一遍并截图；不能的话，给用户列出具体验收步骤。

### 6. 用户验收

给用户一个 3～5 步的验收清单，其中包括"刷新一次页面"。等用户确认。不满意就接着改；改乱了，提醒用户可以点自己那条消息旁边的 Restore checkpoint 退回。

### 7. 收尾存档

- 更新 `docs/进度.md`：已完成功能、数据 key、已知问题。
- 在 `docs/验收清单.md` 里为新功能加 1～3 条检查。
- 用户确认后提交，提交说明用中文写清做了什么。
- 用三句大白话总结：改了哪些文件、为什么改、用户怎么用。
