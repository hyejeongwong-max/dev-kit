# 修 Bug

原则：先找到原因再改；只修这一个问题；修完要证明它好了，而且没弄坏别的。用户是编程新手，解释用大白话。

## 流程

```
- [ ] 1. 收集信息
- [ ] 2. 复现
- [ ] 3. 找根因
- [ ] 4. 修复
- [ ] 5. 验证 + 回归检查
- [ ] 6. 记录和提交
```

### 1. 收集信息

用户描述不全时，请用户按这个模板补充：

```text
【我做了什么】
【我期望】
【实际发生】
【报错】（浏览器按 F12 → Console 里的红字整段复制；或终端里的红字）
【截图】
【什么时候开始的】（最近改了什么之后？）
```

告诉用户怎么打开 Console：在浏览器里按 F12（或右键 → 检查），点 Console。

### 2. 复现

先自己复现：看终端输出，跑 `npm run build`；能用浏览器工具就打开页面照着操作，并读控制台。复现不了时，向用户要更具体的步骤，不要凭猜测改代码。

用 `git log` 和 `git diff` 看最近的改动，问题常出在最近一次提交里。

### 3. 找根因

用大白话告诉用户：问题出在哪个文件、为什么会这样。拿不准时说明有几种可能，用加日志等办法确认，不要同时改好几处碰运气。

常见根因：

- **白屏**：渲染时报错（看 Console 第一条红字）；旧数据格式和新代码对不上。
- **数据"没了"**：换了端口、浏览器或网址（localStorage 按地址隔离）；根本没写进 localStorage；被初始值覆盖了。
- **改了没生效**：dev 服务没在运行；浏览器缓存（Cmd + Shift + R 强制刷新）；改错了文件。
- **CORS 报错**：浏览器限制跨站请求，不是代码写错。需要换数据源或加中转服务，先把方案和代价讲给用户，等用户选。
- **端口被占用**：之前的服务没关。

### 4. 修复

最小改动，只修根因，不顺手重构。涉及数据结构的修复必须兼容已有数据。

### 5. 验证 + 回归检查

- `npm run build` 通过；有测试就跑测试。
- 按用户原来的操作步骤再走一遍，确认好了。
- 按 `docs/验收清单.md` 检查相关功能没被弄坏。
- 请用户亲自再确认一遍。

### 6. 记录和提交

- 这个 bug 容易再犯时，在验收清单里加一条检查；项目有测试的话补一个测试。
- 更新 `docs/进度.md` 的"已知问题"。
- 用户确认后提交，说明写"修复：……"。
- 如果是新手容易踩的通用坑，问用户要不要用 `/dev-handbook` 记进飞书手册。
